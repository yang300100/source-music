音源引擎设计 — 壳与音源分离的核心

两套接口并行：ArkTS 原生音源 + JS 脚本兼容层，两者走同一套标准数据格式

🎯 给哥哥看的效果：怎么用？

用户打开 App → 进入音源管理 → 点「导入音源」：

📄 选本地 JS 文件（从原版 lx-music 社区下载的 .js 音源脚本）→ 自动跑在沙箱里 → 搜歌接口立即可用

🔗 粘贴在线链接（别人分享的音源 URL）→ 下载 → 同样的沙箱执行

📦 安装 .hap 音源插件（未来有开发者用 ArkTS 写的原生音源）→ 性能更好、能调鸿蒙原生能力

每个音源可以单独开关、拖拽排序优先级。搜歌时多个音源一起搜，自动去重合并。

⚖️ 两套方案对比

JS 脚本兼容模式 ArkTS 原生音源
生态 ✅ 直接复用社区现成音源 ❌ 需从零建立生态
性能 ⚠️ 沙箱有额外开销但可接受 ✅ 原生性能，无中间层
安全性 ✅ 沙箱隔离，限制网络/文件访问 ✅ 应用沙箱 + 权限控制
鸿蒙特性 ❌ 无法调用鸿蒙原生能力 ✅ 可调用全部 ArkUI/系统能力
维护 ⚠️ 依赖 QuickJS 编译和适配 ✅ 纯 ArkTS，标准工具链
适合场景 MVP 快速上线、社区音源迁移 深度定制音源、商业音源合作

🛡️ 安全保障

JS 沙箱会限制这些

  • 只能访问音源接口定义的 API
  • 网络请求限速 + 只允许白名单域名
  • 无法访问文件系统（除了自己的配置）
  • 无法调用系统 API 或设备信息
  • 超时自动终止（30秒）

这些做不到

  • 不能读写用户文件
  • 不能获取设备定位/通讯录等隐私
  • 不能在后台偷偷运行
  • 不能绕过 App 的网络代理设置
  • 沙箱崩溃不影响主 App
